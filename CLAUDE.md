# CLAUDE.md — Moquin Press QA Checklist System

Reference notes for working on this app. See also `REGRESSION_CHECKLIST.md` (manual test checklist) and `cloudflare-backend/src/index.js` (backend source, gitignored from GitHub Pages but tracked here locally).

## Architecture

- **Frontend**: single file `index.html` — plain HTML/CSS/JS, no build step, no framework. Deployed to **two** hosts from the same GitHub repo/branch: GitHub Pages at `https://anthonymancino222.github.io/qa-checklist/` (original, kept alive during the sign-in transition) and Cloudflare Pages at `https://moquin-qa-checklist.pages.dev` (added for Cloudflare Access-adjacent reasons, though the actual login ended up being Google Sign-In, not Access — see below). Push to `main` on `https://github.com/anthonymancino222/qa-checklist.git` → both update, GitHub Pages in ~15–30s (CDN cache lag; a fetch with `cache: 'no-store'` right after push often still shows stale content for the first ~15s — wait and retry rather than assuming the push failed), Cloudflare Pages usually faster since it's connected via git integration (Workers & Pages → qa-checklist-backend project → Connect to Git, already authorized to `anthonymancino222/qa-checklist`). GitHub Pages source is **"Deploy from a branch"** (main, /root), not "GitHub Actions" — see the outage note below for why. Verifying what's actually live on either host: `Invoke-WebRequest` with a cache-busting query param and compare against the local file's line count (`(Get-Content file).Count`) rather than raw string/byte length — CRLF-vs-LF alone can make byte lengths differ by tens of KB with zero real content difference.
- **GitHub Pages reliability gotcha**: deploys can get stuck indefinitely in `deployment_queued` — seen for several hours straight on this repo, caused by a stale/orphaned deployment jamming the Pages environment queue, compounded by (that same day) a real GitHub-wide "Partial System Outage." Check `https://www.githubstatus.com/api/v2/status.json` before assuming it's a repo config problem. Fixes that worked: toggling Settings → Pages source away from "GitHub Actions" and back (regenerates the environment binding — may require re-creating a `.github/workflows/*.yml` via the suggested "Static HTML" template if the source toggle clears whatever was driving deploys), then simply waiting for any active GitHub outage to clear. Retrying pushes alone did not help while the outage was ongoing.
- **Backend**: Cloudflare Worker `qa-checklist-backend` (source at `cloudflare-backend/src/index.js`, **gitignored** — not pushed to GitHub, deployed manually/via API, see below). Base URL: `https://qa-checklist-backend.anthony-mancino2.workers.dev`. Data store: Cloudflare D1 database `qa-checklist-db` (one `records` table, JSON blob per record — see `cloudflare-backend/schema.sql`).
- **Auth**: every `/records` and `/photo` request (reads included — reads used to be open, meaning anyone who found the URL could read every job/customer record with no password) now needs EITHER a Google ID token (`Authorization: Bearer …`, real signature verified against Google's own keys, must carry `hd=moquinpress.com`) or the legacy shared key `X-API-Key: MoquinQA2026SecureKeyAlpha7`. The legacy key is a deliberate **transition-window** fallback — see "Google Sign-In" below — not a permanent second auth path; it should eventually be rotated out (tracked, not yet done as of this writing — waiting on confirmation every floor device has actually signed in with `docshare@moquinpress.com` at least once).
- **Sync model**: offline-first. Every save writes to `localStorage` immediately; a background push/pull (`_syncPushAll`, `_syncPullAndMerge`, `_syncNowAll`) reconciles with the Worker. Retries every 30s and on `online` event. Same-id conflicts: local wins (no overwrite) except server-side deletes always win (pruned locally on pull) to avoid resurrecting deleted records.
- **Manual sync**: header "🔄 Sync" button (`headerSyncNowClick()`) next to DATA EDIT — pushes pending, pulls fresh, re-renders the current screen, updates nav badges.

## Google Sign-In & identity

The app now requires signing in with a real `@moquinpress.com` Google account before showing anything — `#google-signin-overlay` sits at the very top of `<body>`, `#appLayout` defaults to `display:none`, and `_onGoogleSignIn()` is what reveals the real app. This isn't just a network gate: it's also what stops a shared floor tablet from displaying whatever job data a *previous* shift's login already cached into that device's `localStorage`, since local data isn't network-gated on its own.

- **Client ID**: `588376109764-m9ma8k76d5fttujgq0mq6u1oa6d0kblu.apps.googleusercontent.com` — the `GOOGLE_CLIENT_ID` constant in `index.html` (safe to be public, unlike the API key) and the `GOOGLE_CLIENT_ID` Worker var (plain text). Both must match. From OAuth client "Moquin QA Checklist Web" in the **QA Photo Storage** Google Cloud project (same project as the Drive service account) — Authorized JavaScript origins there list both hosting URLs (`https://moquin-qa-checklist.pages.dev` and `https://anthonymancino222.github.io`), no path, no trailing slash. Adding a third hosting URL later means adding a third origin there too, or sign-in will fail with `origin_mismatch`.
- **Consent screen is Internal** (Google Auth Platform → Audience, in that same GCP project) — this means Google itself refuses sign-in from any non-`moquinpress.com` account before it ever reaches this app's code, no verification review needed. The Worker's own `hd` claim check in `verifyGoogleIdToken()` is defense-in-depth on top of that, not the only thing stopping an outside account.
- **Real per-person identity, not just a login wall**: the Worker (`checkAuth()`/`verifyGoogleIdToken()`) does a genuine RS256 signature check against Google's own published keys (`https://www.googleapis.com/oauth2/v3/certs`, cached ~1hr) — an unverified JWT is just a claim, anyone can forge one. Checks `aud` (this app), `iss` (really Google), `exp` (not expired), `hd` (really moquinpress.com) before trusting `email`/`name`.
- **Persistent sign-in — two independent layers**: originally this was *only* `auto_select: true` + `google.accounts.id.prompt()`, which turned out to be unreliable as the sole mechanism — a browser privacy setting, an expired Google browser session, or someone having dismissed the One Tap prompt once before can all make the silent resume fail with no error, forcing a real sign-in far more often than intended (users were being asked to sign in on nearly every reopen, not just after real inactivity). Fixed by adding a real local session on top:
  - **`_LOCAL_SESSION_KEY` (`qa_local_session_v1`) in `localStorage`** is the actual "stay signed in" mechanism now — `{name, email, idToken, lastActivityAt}`, written by `_saveLocalSession()` on every successful sign-in. `_tryRestoreLocalSession()` runs on every page load *before* anything Google-related, and if a valid (≤12h since `lastActivityAt`) session exists, it skips the sign-in overlay and restores the identity immediately — zero dependency on Google's own resume succeeding. `lastActivityAt` refreshes (throttled to once/minute) on any click/keydown/touchstart via `_touchLocalSessionActivity()`, so the 12h window is inactivity-based, not fixed-since-login.
  - **`auto_select: true` + `google.accounts.id.prompt()`** (on load, and again every 45 min since tokens expire ~1hr) still run afterward on a best-effort basis — this is now just how `_googleIdToken` gets refreshed with a real, backend-verifiable token in the background; its failure no longer bounces anyone back to a manual sign-in screen.
  - Either layer's user is cosmetic only client-side (per the existing "not a verification step" note below) — the real server-side check is unchanged. Explicit **Sign out** (`_signOutOfApp()`) clears both: `disableAutoSelect()` so Google's own resume won't silently fire next time, and `_clearLocalSession()` so the local session is gone too.
- **Real-world account shape** (as of this writing): floor tablets all sign in as one shared `docshare@moquinpress.com` — no individual attribution for floor-submitted entries, which is *less* specific than the typed/picked operator name field on each form, so that typed name stays the real "who did the work" for floor stages. `anthony.mancino@moquinpress.com` and `mathias@moquinpress.com` are individual accounts on their own devices, used for DATA EDIT specifically — see below.
- **DATA EDIT is restricted by email**, not just the old passcode (`DATA_EDIT_ALLOWED_EMAILS` array in `index.html`, currently Anthony + Mathias) — the passcode alone was never real protection since it sits in this same public page's source. The header button and in-popup button both default to hidden and only reveal for an allowed email (`_applyDataEditVisibility()`, and the job-stage check in `_renderProdSummary`); `toggleDataEditMode()` itself also checks (`_isDataEditAllowedUser()`), so a bypass of the hidden buttons still hits a block with a plain alert, never reaching the passcode prompt. The passcode itself is unchanged as a second step for allowed accounts.
- **DATA EDIT audit trail**: every edit (`_saveEditJobStation/Operator/CadStyle/QtyExec…`) and delete (`deleteIPJob`, `_cmDeleteJob`, `_shipDeleteJob`, `deleteRecordEntry`) now writes a `stage: 'data_edit'` entry into the job's own `stageHistory` via `_logDataEditAudit()` — nothing did this before, edits and deletes had zero audit trail, not even the typed operator name floor stages get. `_stageSnapshot()` stamps `signedInAs` (the actual signed-in email) on *every* stage entry unconditionally, not just data_edit ones — accurate either way, just more individually meaningful for a named account than a shared one. Deletes route through `_logDataEditAuditThenDelete()`, which writes+pushes the audit entry **before** the delete request — getting that order backwards would let the bulk-upsert endpoint's `deleted = 0` on-conflict clause resurrect the very record the audit was trying to document.

## Backend deployment (no local Node/wrangler available in this environment)

Two ways to deploy the Worker, in order of preference:

1. **Directly via the Cloudflare API** (preferred when a Cloudflare API token is available — see the account's `cf_creds.json` pattern used in past sessions, scoped narrowly to Workers Scripts/Pages/Access:Edit, short TTL). `PUT /accounts/:id/workers/scripts/qa-checklist-backend` with a multipart body: a `metadata` JSON part (`main_module`, `compatibility_date`, `bindings` array) + a `worker.js` part with the **raw file bytes read directly off disk** (`[System.IO.File]::ReadAllBytes(...)` in PowerShell) — never hand-retyped or passed through a browser clipboard, which has been proven to silently corrupt a byte in transit (caught via a SHA-256 hash mismatch during this same rollout). Secret bindings (`API_KEY`, `GOOGLE_SA_PRIVATE_KEY`) are safe to **omit** from the upload metadata — verified empirically against a disposable throwaway Worker before ever risking it on the real one: set a secret, upload a new version that never mentions it, confirm via a live fetch that the secret's actual value survived untouched. Every *other* binding (D1, plain-text vars) must be explicitly re-declared in the metadata every time, since only secrets get this special preservation-on-omission treatment.
2. **The Cloudflare dashboard's in-browser code editor (Quick Edit)**, via `claude-in-chrome` or manual copy-paste, when a Cloudflare API token isn't set up. `read_page`/`computer` screenshots on `dash.cloudflare.com` can intermittently need a fresh per-tab permission grant after an internal page reload — if a previously-working browser session suddenly can't screenshot/read the page, that's most likely an unanswered permission prompt, not a hard platform block; closing and recreating the tab has resolved it. **Large pastes via automated typing are unreliable** even once connected — has corrupted the editor mid-paste before (stray keystrokes opened command-palette/search overlays, or dropped a chunk of text). For anything beyond a one-line edit, prefer having the user paste the code manually (Ctrl+A, Ctrl+V, Deploy) over automating it — verify with a fresh `Ctrl+Home` → `Ctrl+Shift+End` check before deploying, and if in doubt, **discard and reload** rather than risk deploying broken code (the live Worker keeps its last-good version until Deploy is actually clicked).

Either way: editing env vars manually is Overview → Settings → "Variables and secrets" → Add/Edit → Type **Secret** for anything sensitive, **Text** for plain config → Deploy. The dashboard also surfaces unrelated upsell/onboarding flows (an "Enable Agent Lee access" panel, a "Cloudflare Zero Trust — choose a plan" page) that can appear from stray clicks/keystrokes — back out of these (Cancel/X), never grant access or select a plan.

## Daily database backup

`scheduled()` in the Worker runs once a day (cron trigger set via `PUT /accounts/:id/workers/scripts/qa-checklist-backend/schedules`, body `[{"cron":"0 10 * * *"}]` — 10:00 UTC, ~3am Pacific, off-hours; no wrangler.toml in play so this has to be set via the API, not a config file). `runBackup()` dumps the **entire** `records` table — every job/NCR/NCR draft/qc_draft, deleted rows included, not filtered by type — into one dated JSON file (`qa-backup-<date>-<timestamp>.json`), uploaded via the same service-account Drive flow the photos already use, into a **separate** folder from photos: the "QA Backups" folder (id in the `GOOGLE_BACKUP_FOLDER_ID` Worker var) inside the same "QA Photos" Shared Drive.

- **`POST /admin/backup-now`** (same auth as everything else) triggers `runBackup()` on demand — exists so a backup can be verified/triggered immediately rather than only trusting an unwatched cron for up to 24 hours. Returns `{ok, backup: {fileId, filename, recordCount, exportedAt}}`.
- **No pruning/retention logic yet** — every day's backup accumulates forever. Deliberate simplification: this is plain JSON text (not photos), so even years of accumulated daily backups is unlikely to be a real storage cost at this app's volume. Revisit if that stops being true; don't add retention-tiering complexity speculatively.
- **Retention window** (SQF-driven — see the Data Handbook artifact from this rollout): a 3-year *minimum* was the number actually confirmed, chosen as a safe placeholder above the practical "keep until next recertification audit" floor rather than because SQF itself specifies a number (it doesn't — SQF 2.2.2.3 just says "as specified by a customer or regulation"). Since nothing is pruned, this requirement is trivially satisfied for now regardless of the exact number.

## Restoring from a backup

`POST /admin/restore-record` body `{fileId, recordId}` restores **one** record from **one** named backup file — find the backup's Drive file id (open it in the "QA Backups" folder, or read it off a prior `/admin/backup-now` response), find the record's own `id` (the job number isn't the same thing — it's `record.data.jobNumber`, not `record.id`), then `POST` those two values. The endpoint fetches that exact file from Drive, finds the matching record inside its `records` array, and re-`INSERT ... ON CONFLICT DO UPDATE`s it into D1 — the same upsert shape every other write already uses.

- **Deliberately not a whole-database restore.** The bulk-upsert SQL has no "only if the incoming version is newer" check — replaying an entire backup over the live database would silently overwrite any record that changed *since* that backup with the older snapshot. A targeted single-record restore can't clobber anything it wasn't pointed at. If a real whole-database disaster ever happens, the fix reuses this same fetch-and-parse logic in a loop — but that's a decision for whoever's actually holding the outage to make deliberately in the moment, with eyes on what's about to get overwritten, not a pre-built button that makes it too easy to skip that judgment call.
- **Verified end-to-end, not just written and trusted**: created a disposable test record → triggered a real backup (captured it) → deleted the test record (confirmed gone) → restored it from that exact backup file → confirmed it came back with byte-for-byte the same data and the deleted flag correctly cleared → deleted the test record again for real. The one test backup file this created was left in the QA Backups folder rather than hunted down and deleted — it's an accurate historical snapshot like any other daily backup, not pollution, and tampering with backup history to erase test evidence would cut against the whole point of keeping it.

## Google Drive photo storage

Photos (make-ready, QA release, NCR, RCA) are uploaded to a Google Drive **Shared Drive** and referenced by a backend-proxied link instead of being embedded as base64 in synced job/NCR/RCA records (which was filling up `localStorage`).

- **Why a Shared Drive, not a regular "My Drive" folder**: a service account has zero storage quota of its own. Even when a personal folder is *shared* with the service account, uploading into it still fails with `storageQuotaExceeded` — the service account is the file's creator/owner, and owners need real quota. A Shared Drive owns its files itself, sidestepping that entirely. Both the upload and retrieval Drive API calls need `&supportsAllDrives=true` for this to work against a Shared Drive.
- **Service account**: `qa-photo-uploader@qa-photo-storage.iam.gserviceaccount.com` (Google Cloud project `qa-photo-storage`), scope `drive.file`, added as a **Content Manager** member of the Shared Drive.
- **Secrets** (set as Cloudflare Worker secrets/vars — never committed to the repo): `GOOGLE_SA_EMAIL` (plaintext), `GOOGLE_SA_PRIVATE_KEY` (secret — the PEM from the service account's JSON key; needs real/stripped whitespace, not literal `\n` — see `pemToArrayBuffer` in the backend), `GOOGLE_DRIVE_FOLDER_ID` (plaintext — currently the Shared Drive's own ID, `0AHhuh7Nddb6UUk9PVA`).
- **Backend endpoints**: `POST /photo` (auth required, body `{filename, mimeType, dataBase64}` → `{id, url}`) uploads via a JWT-signed (RS256, Web Crypto) service-account token exchanged at Google's OAuth token endpoint; `GET /photo/:id` (no auth — id itself is unguessable) proxies the file bytes back through the Worker using the same service-account token, so the Drive file stays **private** and the browser never needs its own Google auth to display it.
- **Frontend helper**: `_uploadPhotoToDrive(dataUrl)` in `index.html` — POSTs the captured photo, returns the backend proxy URL (`QA_BACKEND_URL + result.url`). **On any failure it resolves to the original data URL unchanged** — a photo must never be lost to a flaky shop-floor connection; worst case it just falls back to the old embedded-base64 behavior for that one photo. Wired into every photo-commit point: `submitForQAApproval`, `beginVeritivPacking`, `beginInspection` (Kama/DC/Gluer, both production and make-ready branches), `submitJob` (Bindery/Pressroom Cutter + non-Veritiv Packing multi-product path), NCR photo capture, RCA photo capture.
- Photos taken/synced **before** this was added remain stored as base64 — no retroactive migration was done; only new captures go through Drive.

## Deleted Items admin view (undo-delete)

A **"🗑️ Deleted Items"** button (`#qamgr-deleted-items-btn`, inside QA Manager — see below) opens `#deletedItemsOverlay` — a plain list of every deleted job and NCR record, each with a **Restore** button. This is the practical answer to "delete was always soft (a `deleted` flag, never an actual erase) but there was no way to *use* that short of hand-editing the database" — no backend changes were needed for it, since `GET /records?type=X` already returns deleted rows (the normal sync path just filters them out) and `PUT /records/:id` already clears `deleted` on any upsert.

- **Same gating as DATA EDIT** — `_applyDataEditVisibility()` shows/hides the QA Manager tile alongside the DATA EDIT button (allowed emails only), and `openDeletedItemsView()`/`restoreDeletedRecord()` each independently re-check `_isDataEditAllowedUser()` before doing anything, so hiding the tile is a convenience, not the actual security boundary.
- **Scoped to `job` and `ncr` only** — the two types actually deleted through a UI button. `ncr_draft` is pre-submission scratch state (nothing worth restoring); `rca` isn't synced to the backend at all yet, so there's no server-side `deleted` flag to undo in the first place.
- `_loadAndRenderDeletedItems()` fetches both types, keeps only `deleted === true`, sorts most-recently-deleted first, and renders via `_renderDeletedItemsList()` (with a plain empty-state message once nothing's left).
- `restoreDeletedRecord(idx)` confirms, then `PUT`s the record's own data back (clearing `deleted` server-side), adds it back into the in-memory `ipLoad()`/`ncrLoad()` list, and — for jobs only, since NCRs have no `stageHistory` — writes a "Job Restored" entry via `_stageSnapshot()` so the restore itself is audited (who, when), same reasoning as every other DATA EDIT action.
- **Tested against the live backend**: confirmed the button/action are both independently blocked for a non-allowed signed-in account (verified via the overlay's actual open/closed state, not leftover dialog text), confirmed only genuinely-deleted records appear and in the right order, and confirmed a full delete→restore round trip via the real Cloudflare Worker brings a record back with its data and stage history intact.

## Schedule bridge (job/customer/product/die autocomplete)

The app never talks to CERM directly (standing rule — see cross-session memory `no-cerm-server-access`). Instead Anthony manually exports the day's job schedule out of CERM as `.xlsx` and drops it into a Shared Drive folder (id `0AMipwK6rTWFBUk9PVA`, shared as **Viewer** onto the existing `qa-photo-uploader@qa-photo-storage.iam.gserviceaccount.com` service account) — this is the "bridge." The app pulls from that bridge, never from CERM itself.

- **Backend**: `GET /admin/schedule-pull` (auth required, same as every other endpoint) — reads the *newest* `.xlsx` in that folder (multiple exports a day is expected, not "one file per day"), parses it, and returns `{ ok, sourceFile, fetchedAt, jobCount, jobs: { jobNumber: {customer, products, dieNumbers} } }`.
- **No xlsx library** — there's no npm bundler in this Worker's deploy path (see "Backend deployment" above), so `parseScheduleXlsx()` hand-rolls just enough of the format: an `.xlsx` is a zip of XML, and Workers' native `DecompressionStream('deflate-raw')` inflates zip's DEFLATE entries with zero dependencies. XML is parsed with regexes (safe here since Excel's own output is a fixed, well-formed shape, not arbitrary XML) rather than a DOM parser, since Workers has none built in.
- **Drive scope had to be widened**: `getDriveAccessToken()`'s JWT originally requested only `drive.file` (files the service account itself created — fine for photo/backup uploads). That scope can't see a folder merely *shared* with the account by someone else, so the schedule-pull needs `drive.readonly` added alongside it (space-separated in the same JWT `scope` claim) — found this the hard way when the first deploy returned "no .xlsx files found" despite the folder genuinely having files and being shared correctly.
- **Sheets are read generically by header row, not by name** — Anthony's export has one tab per production station (`FolderGluer`, `DieCutter`, `LabelCutter` today, more may be added). A sheet whose header row includes `Components` is treated as a die-number sheet; any other sheet with a `Job` column contributes `Customer` + `Station / Product`. A job can appear on multiple sheets/rows, so products and die numbers are de-duplicated sets, not overwritten.
- **Die number extraction rule** (Anthony's own rule, verified against his screenshots): the DieCutter tab's `Components` cell holds several newline-separated lines like `Blanker bottom / 9184-F1-B / CR-06 / ...` — the die number is the leading digits of the **second** slash-separated field (`9184`), ignoring the `-F1-B` suffix and everything else on the line. See `extractDieNumbers()`.
- **Frontend**: a "🔄 Pull Schedule" button on the QC setup screen (deliberately manual for now, not an automatic background fetch, per how Anthony first scoped this — see him before making it automatic) calls `pullScheduleNow()`, caching the result in memory only (`_scheduleData`, not localStorage — it's a live in-progress-jobs snapshot, not something that should look "current" after sitting stale for days). Typing into the Job number field (`filterJobSchedule()`) shows a type-ahead dropdown styled like the existing customer combo; picking a job auto-fills Customer and Product (only when there's exactly one product — with several, they're left for the person to pick, shown in a "From schedule — ..." hint line under the field rather than guessed at). Die numbers are shown in that same hint line, since there's no dedicated "die number" field in the job form yet — that's a future decision, not implemented.

## Workflow — who pushes what

The user has granted standing permission for Claude to directly execute deploys in this project — push to GitHub, deploy/edit the Cloudflare Worker, edit the Apps Script backend — without asking each time. This has been the actual working pattern across multiple sessions: Claude runs `git add`/`commit`/`push` directly via PowerShell, and edits/deploys the Worker through a connected Cloudflare dashboard browser tab. **Permission is granted broadly; what actually blocks Claude is capability, not permission** — three distinct kinds of block have been confirmed, and none of them can be talked past by the user saying "you have permission":
1. **Domain allowlist** — `github.com`, Cloudflare Console, and Google Cloud Console are outright-blocked domains for the `claude-in-chrome` browser tool. Confirmed repeatedly: even explicit "you have permission to navigate there" in chat does not lift this. `script.google.com` / `docs.google.com` are *not* blocked for navigation/clicking, but see the next point.
2. **Content-reading restriction on Google domains** — on `script.google.com`/`docs.google.com`, `screenshot` and `get_page_text` are blocked (privacy protection on the user's account content) even though `navigate`/`computer` click actions work fine. Verify state there by describing click results or via direct HTTP calls (PowerShell `Invoke-WebRequest` against a public API/doGet endpoint) — never by trying to screenshot.
3. **Risky-action safety classifier** — a separate check (independent of both of the above) can block one specific *action* it judges too risky to automate, e.g. it blocked an autonomous click on Apps Script's "Deploy" button specifically, mid-session, after permission had already been established and other clicks on the same page had gone through fine. When this happens, stop retrying that exact action and hand it back to the user with precise click-by-click instructions.

For anything hitting one of the above, the user has stepped in directly:
- Google Cloud Console setup (creating the project, service account, and Shared Drive), and any Cloudflare/Google Cloud Console navigation.
- The Apps Script "Deploy" button click (blocked by the classifier — see above), and manual copy-paste into the Apps Script code editor for large/multi-line changes (Claude edits the local `.gs` file and hands the user the diff to paste; typing large pastes into that editor directly has corrupted it before — see "Backend deployment" gotchas above).
- The Gluer Shift Handoff app's GitHub upload step specifically, since that app isn't a git repo (see cross-session memory `reference-gluer-shift-handoff-deploy` / `project-moquin-press-apps-overview`) and its deploy path runs through the blocked `github.com` domain.
- Anything requiring their own Google/Cloudflare/GitHub account login, or approving a new domain/tab connection.

**Instruction for future sessions**: keep this same division of labor by default — don't ask "can I push this?" or "can I deploy this?", just do it. Only hand a step back to the user when one of the three capability blocks above is actually hit, and say so explicitly and specifically (which of the three, not just "I can't") rather than silently retrying or giving up vaguely.
